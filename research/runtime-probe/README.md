# Runtime-aware discovery feasibility

Two unchanged Rust IL2CPP probes completed against Blue Prince on 2026-10-21,
without screenshots, gameplay input, game-specific name rules or offsets. Each
enumerated 16,955 types and 87,225 fields, and read 989 live scalar storage
locations. Of those, 38 belonged to the game's main Assembly-CSharp image.
Twelve scalar values differed between inspections; 977 were equal.

This supports adding runtime structure as a discovery source. It does **not**
establish 989 useful controls. Most live values belong to libraries; names are
hypotheses, some static storage contains zero/default values, and managed class
constructor completion was not checked. The adapter obtained metadata for
51,837 instance fields but did not resolve their live objects. No gameplay
authority, working health/ammo edits, object lifetime handling, restart recovery,
or generalization acceptance is claimed. Progress remains **31%**.

## Method and evidence

- [Protocol](PROTOCOL.md) and [source/binary freeze](frozen-v1.json), recorded
  before native evaluation. All 17 frozen source/binary files verified unchanged.
- [Results and artifact hashes](results.json), generated by the explicitly
  post-run [audit](audit_postrun.py). Raw reports remain local under
  `test-results/runtime-probe-v1`; the full game metadata is not redistributed.
- An owned ABI mock passed two inspections and four rejection cases (creation
  identity, session, helper hash, existing output). It verified scalar decoding,
  changing values, unsupported-field abstention and helper unloading. It is not
  an independent IL2CPP implementation.
- Same frozen helper then ran twice on the installed real IL2CPP game, PID 78240,
  creation `01dd615582524cbc`, Anode session 2. Steam stayed in session 1. No save
  was selected and no player input was sent.
- Both game reports had zero enumeration omissions or text decoding errors.
  Enumeration took 1,335 and 1,296 ms; the full load/inspect/unload cycles took
  14,107 and 14,235 ms. Do not substitute enumeration time for total latency.
- Game remained responsive with its window present and helper absent. The owned
  game exited after its window was closed; fixture and command jobs also exited.
  Anode lease was released. Desktop Reversebolt PID 67560 remains unchanged.

The first parent-session process query returned a zero main-window handle; Anode
window enumeration and a session-2 query confirmed the actual game window. This
was a cross-session observation limit, not a failed game probe or rerun.

Rust unit tests, build, formatting and strict Clippy pass for this standalone
workspace. Production crates were not changed and their tests were not repeated.

## Access model and limits

This is **explicit in-process instrumentation**, not passive external reading.
The loader allocates arguments, loads our pinned helper DLL, starts its inspection
thread, waits for completion, then unloads it. Runtime metadata APIs may initialize
metadata/storage and perturb timing and allocation. The helper calls no managed
property getters, class constructor entry points, arbitrary methods, field setters
or GC-control functions. Scalar reads use ReadProcessMemory and are not atomic.
Static storage availability does not establish that its class constructor ran.

API providers are selected by capabilities; field names are never used to decide
what to inspect. The adapter reads public type codes, field flags, offsets and
static-storage bounds. Literals, open generics, unsupported types and instance
fields remain metadata-only. The fake runtime also exercises a thread-static
sentinel outside storage bounds. No private Il2CppClass layout is embedded.

Windows x64 and the observed API contract are the tested scope. The owned ABI
mock does not establish support for other Unity releases. Export stripping,
obfuscation, ABI changes, other engines, uninitialized classes and object
lifetimes remain limits. A stuck API call cannot be safely cancelled mid-call.
The loader retains arguments and helper on uncertain termination and emits a
thread receipt; a future runner must recover that state rather than retry.
Large metadata output also needs incremental delivery before product integration.

## Decision and next work

Prioritize runtime-derived candidates and live object/reference discovery through
the shared engine/MCP model, retaining behavioural memory discovery as a fallback.
Use observation and controlled tests to determine which fields affect relevant
behaviour. Cache stable schema, limit live traversal and surface only ranked,
understandable cards. Do not place this metadata report in the user-facing app or
automatically load a helper merely because an application was selected.

The next runtime milestone is resolving live instance roots and references with
an explicit lifetime contract, establishing relevant values across updates, and
testing that an intervention changes behaviour. Supporting an engine/runtime
preserves generalization across its games; game-specific layouts remain excluded.

## Sources and reproduction

Bindings were written against Unity's official
[IL2CPP API declarations](https://raw.githubusercontent.com/Unity-Technologies/SimpleUIDemo/master/Tiny3D/Library/DotsRuntimeBuild/artifacts/Stevedore/il2cpp/libil2cpp/il2cpp-api-functions.h).
Its [API implementation](https://raw.githubusercontent.com/Unity-Technologies/SimpleUIDemo/master/Tiny3D/Library/DotsRuntimeBuild/artifacts/Stevedore/il2cpp/libil2cpp/il2cpp-api.cpp)
documents static-data access. Only signatures/contracts were used; no Unity or
game implementation was copied. These older published sources do not guarantee
every future ABI. [Unity's backend documentation](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/scripting-backends/intro)
explains why IL2CPP and Mono need distinct access paths.

Build from the repository root with `cargo build --manifest-path
research/runtime-probe/Cargo.toml --target-dir target/runtime-probe --offline`.
Run the owned `mock_case.py` inside a leased Anode session with a new output
directory. `game_case.py` requires an explicitly launched game PID, exact creation
identity, session and new output directory. Use Anode's Steam launcher and retain
the current user's desktop Steam. Never overwrite or silently rerun the recorded
v1 cases. This workspace is research-only and is not part of the shipping build.
