# Memory-only trajectory proposals

Implemented 2026-10-22. Full-goal progress remains **35%**. This is an offline
candidate producer in the Rust core, using saved broad-memory exports. It does not
name gameplay controls, authorize edits, or publish unidentified desktop cards.

## Policy

`memory_order_trajectories_v2` requires at least twelve memory samples from one
frozen batch. It selects using the first six; all later samples are assessment
only. Image-only captures are skipped, preserving original capture numbers.
Images, OCR values, labels, inputs, process names and runtime metadata do not enter
the selection. The original sampling plan may still have been screen-guided.

Each complete prefix chunk is scanned as naturally aligned little-endian I32,
F32 and F64 values, using the existing generic numeric prior: finite values,
absolute value at most 1e12, and either zero or at least 1e-12. Constant bytes and
values changing fewer than twice in the prefix are excluded. Missing prefix reads
exclude that chunk; they are never replaced by zero. No values span chunk boundaries.

Qualifying sequences are grouped by their six-value weak order: which values are
equal and which are larger. Canonical reversal groups opposite directions too.
This groups affine copies but also unrelated coincident sequences. It neither
deduplicates representations nor establishes a shared object, variable or cause.

At most 128 groups are retained. Two-level groups come first, then monotonic
groups, then other groups; fewer distinct levels and a fixed hash break ties.
Each group retains at most four address-sampled representatives **per numeric
type**, up to twelve members. This is a declared behavioral prior, not a learned
score of gameplay importance. Counts include all qualifying candidates, and the
result reports omitted groups and members. Address sampling can miss a useful
field and can change under relocation.

Later samples check only preselected two-level or monotonic patterns. A new level
or a reversed adjacent step contradicts those patterns. Three usable checks are
required for `consistent`; otherwise the result is `insufficient`. Varying
sequences have no forecast and return `not_predicted`. Missing/invalid values do
not bridge monotonicity comparisons. No assessment changes prefix selection,
ordering or counts. Consistency on later bytes of the same recording does not
establish gameplay meaning, allocation continuity, independence or causality.

## Evidence and failure-driven revision

An initial unpublished v1 used eight representatives per group without separating
types. In a generated noisy recording it omitted the planted F32 sequence because
integer views filled that group. The exact initial source, test log and report are
preserved in `test-results/memory-trajectories-initial-v1`. V2 reserves space for
each type. This is a change informed by an exposed synthetic example, not a
withheld evaluation or proof of generalization.

The tests use generated byte arrays with known sequences, unrelated random words,
static fields, late-only changes, aliases, missing reads and a pattern that changes
after selection. They check selection invariance under changed future data,
misleading labels, final mapping flags and chunk order. Both I32 and F32 views of
one location survive; an opposing copy remains a separate candidate. Short/static
recordings produce no invented candidates. Corruption in a later segment is
detected even when the chunk was excluded for a missing prefix read.

A twelve-seed generated measurement records recovery and omissions without
asserting that every planted sequence must be found. [Results](results.json)
contain the per-sequence counts, timings, test logs and frozen source references.
No independent game, native process, model or production application is run.

| Planted typed sequence | Retained across 12 backgrounds |
| --- | ---: |
| Two-level I32 sequence | 12/12 |
| Increasing F32 sequence | 12/12 |
| Varying F64 sequence | 12/12 |
| Opposing I32 copy | 12/12 |
| Increasing I32 counter | **0/12** |
| Two-level I32 prefix that later changes to a third level | 12/12; all contradicted |

These backgrounds change random words while keeping planted layouts and sequences
fixed. They are not independent implementations or withheld game tests. Each run
retains 518–526 typed proposals; 510–517 have no forecast, and only three meet the
limited later-consistency check. The I32 counter still loses the representative
lottery within a large group. Observed analysis times are 7–11 ms for 128 KiB of
planned ranges across twelve samples (1.5 MiB payload), not a large-game benchmark.
On the exact same archived noise example, v1 retained 1,014 members and missed the
F32; v2 retains 523 and preserves it. There is no claim of semantic precision.

All **417 workspace tests** pass, with the eight new integration tests rerun after
test-only cleanup. Strict workspace/all-target Clippy and formatting pass. The
first Clippy run requested fixed-size array chunks in two fixture loops; changing
their iteration form resolved it without changing the generated bytes.

## Reuse

`memory_evidence::Archive::visit_memory_chunks` streams hash-checked histories
through at most twenty 64 KiB payload buffers at a time, plus bounded metadata and
candidate storage. Every retained segment is checked; a file-read or checksum error
discards the partial analysis. The report binds the original manifest hash and capture split.

`memory_trajectories::analyze(&archive)` is the shared core API. The offline
`memory-trajectories` example accepts the export directory and manifest hash and
prints its JSON report. It never reconnects to a process. This milestone delivered
the offline API/example. [Subsequent integration](../memory-proposals/README.md)
adds automatic final observation review and paged MCP access to its research
proposals, while keeping them separate from editable desktop controls.

## Remaining work

Connect promising trajectories to independently collected behavior and prospective
interventions, preserving competing representations and display copies. A group
with hundreds of similarly timed counters can still omit the controlling value.
There is no semantic naming model, causal verification, byte/word/integer64 support,
unaligned/encoded-field discovery, pointer recovery or durable live binding here.
The old game recordings cannot evaluate this producer because their broad bytes
were discarded. Real-game validation remains unavailable under the existing
Windows security block. All artifacts stay local.
