# Runtime discovery in the product — v1

Freeze the product source revision, runner/host source hashes and exact copied
binaries before native evaluation. Do not change frozen code to reinterpret a
failure as a pass. Preserve each failed run and use a new version after repairs.

This experiment checks the complete application/MCP path, not just the helper.
Use Anode and isolated session directories. The existing runtime-path ABI fixture
is hosted by an owned Python window, with its exact DLL copied from paths v2.
It is an owned simulation, not independent-game evidence.

1. Start the GUI and a real stdio MCP client. Select the fixture window from the
   application's process inventory. Attachment must automatically start exactly
   one managed runtime-discovery step, without screenshots, OCR or model calls.
2. Check nonempty, unique, provisional cards. Refresh the first four candidates
   using the published catalogue/revision and normal MCP job envelope. Await the
   job, verify a new revision and read statuses. Retain all helper receipts.
3. Replay the exact successful request: it must return the same job and start no
   helper. Submit a new request with the stale revision: it must be rejected and
   start no helper. Do not compensate by silently refreshing a different cursor.
4. In the owned fixture only, null the root through its control file. Refresh
   must clear current values, retaining historical candidate observations. Restore
   the structure and read again. Verify balanced pauses and zero helper Rust heap
   operations during pauses. Fixture metadata APIs abort if called while paused.
5. Inspect the GUI's accessibility tree for named cards and Refresh value actions.
   Keep screenshots and game input at zero. Close only owned processes afterward.
6. If the fixture passes, repeat the unchanged connection/discovery/refresh/replay/
   stale-cursor workflow in a fresh Blue Prince process. Select the first four
   published candidates declared outside the runtime-reported core library;
   fall back to the first four if no such values exist. No game-specific field or
   image names influence selection. Record actual names/images only after selection.
   No gameplay writes, menu navigation or save selection. Verify unload and game
   responsiveness, then close the owned game.

Use up to 64 displayed candidates; rank non-core declarations before core values
and distribute candidates across images. This is a structural diversity heuristic,
not a semantic relevance model. Measure selected image distribution, refresh
latency and current values, not just the number of fields read. A candidate called
Speed is not a verified speed control. A collection path identifies its current
occupant, not a persistent actor. Root completion is not complete graph coverage.

The previous advisory turn did not change implementation or produce new native
evidence; it is classified as no progress toward the goal. This experiment resumes
the available implementation/evaluation work. Overall progress stays 31% unless
new evidence earns credit under the existing weighted capability plan.
