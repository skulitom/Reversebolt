# Searchable runtime context — v1

The previous turn delivered the runtime product workflow and is classified as
progress. The next observed bottleneck is selection: 64 displayed cards conceal
other observed paths, and metadata field names such as `value` omit same-object
text. Post-hoc examination of the retained Blue Prince discovery found nine
scalar-bearing objects with readable string references, including labels absent
from the old cards. These are clues, not verified gameplay meanings.

Implementation: retain at most eight direct same-object text references, with
field provenance and truncation flags. Labels do not become path identity. Search
field/type/image/root names and those hints before applying a 20-result page
limit. Keep search anchored to the original canonical report digest, catalogue
and observation time, even after fresh value reads. Showing selected results
must preserve newer readings for existing cards and reject old revisions. New
cards remain historical until explicitly refreshed. Prefer complete text context
within the existing structural priority; encode no game names/offsets/keywords.

Freeze committed sources and six exact binaries before evaluation. Preserve all
failures; source changes after a native failure require a new version and fresh
case. Do not change the prior runtime-product studies or their frozen artifacts.

1. Run core regressions for same-object labels, unread/malformed references,
   stable path identity despite changed labels, filtering beyond 64 results,
   pagination, stale selection, preserved freshness and changed source evidence.
2. Replay the saved product-v2 Blue Prince discovery through the new converter.
   Retain the original input hash. Inspect a fixed exploratory query `RookPos`,
   chosen from that saved evidence, and compare the old/new 64-card selection.
   This is post-hoc evidence reuse, not an independent or held-out discovery test.
3. Run the real GUI/shared engine and stdio MCP with 39 tools in Anode against
   the unchanged owned runtime-path fixture. Automatically discover, search a
   label taken from discovered context (or a field if no labels exist), browse
   beyond the first 64, show up to four results and refresh them. Search/show and
   rejected stale selection must start no helper. Preserve exact refresh replay,
   stale-refresh rejection, null-root invalidation and restored-structure checks.
   If the fixture has fewer than 65 candidates, browse its first page instead;
   that case establishes the workflow, not beyond-display native coverage.
4. If the fixture passes, repeat the unchanged runner on a fresh Blue Prince
   process. Its four selected paths must lie beyond the initially displayed 64.
   No game-specific name, offset or source layout selects them. Verify fresh
   reads, correct cursors, helper unload and game responsiveness. No gameplay
   input, images, save selection or gameplay writes. Close only owned processes.
5. Inspect the new GUI affordance and selected cards through accessibility, then
   verify frozen binary/source and receipt/report hashes, package and update the
   desktop preview if the checks pass. Preserve history and model selection.

Measure search coverage, text provenance, selected path freshness and actual
helper calls. A label can name something other than a gameplay property and can
change when a path's occupant changes. No causal control or generalization
acceptance is claimed without independently checked gameplay effects. Full goal
and 31% weighted progress remain unchanged unless new evidence earns credit.
