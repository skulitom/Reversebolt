# Following changing values — native v1

Freeze product source/executable hashes, this method, fixture and runner before
launch. Run exactly two fresh cases in Anode, slots 0 then 1; retain every failure
without replacement, changed sequences, manual screenshots, or extra captures.
Both use the same owned window with a 32 MiB committed arena and a randomized
aligned field in its upper half, storing half of its displayed number as F32.
The oracle is evaluation-only: never supply its address, layout, type or value
to Reversebolt. Select the owned process using the normal inventory. Use a one
MiB ordinary capture budget, default 128 MiB change-selection ceiling, and no
optional image model. No memory writes or game-specific product logic.

Attach without automatic observation; schedule one full observation using the
normal job API to obtain the number card at 50. Select its lowest active readable
OCR track. Then call start_change_search once with the current scope/track and
normal automatic behavior. Do not call finish_change_search or schedule its
follow-up from the evaluator: the product must own the four-to-sixteen handoff.

Slot 0 selection values: 20, 80, 30, 70. Slot 1: 20, 20, 20, 20. Between captures
change only the owned fixture through its control file. The first fresh value
equals the last selection value (70), avoiding an evaluator race at the automatic
handoff. Slot 0 fresh values are 70,56,31,85,64,27,75,92,44,67,38,50,54,54,50,50.
Preserve pauses/failures and stop on skipped captures. The last selection state
may be read from the product's own batch archive if the automatic transition
completes before polling observes that state; this is declared in advance.

For slot 0, require the actual field to be outside the old ordinary plan, inside
the selected windows, and represented in a frozen fresh F32 hypothesis after
twelve new moments with four later agreements. No old frame or selection frame
may count toward that fresh basis. Report every additional hypothesis separately.
For slot 1, require explicit insufficient-contrast abstention with no fresh batch
or job, selected areas, or prediction checks. Any unrelated failure remains a
failure, not a successful negative result. Read/write bounds and selection
witnesses must be retained for post-run integrity checking.

This verifies bounded workflow and encoded-value selection in synthetic native
windows. It does not establish gameplay authority, hidden meaning, nonlinear
encodings, restart recovery, or independently implemented game acceptance.
