# Prospective hold/change and one-location tests in original Tetris

Freeze this protocol, evaluator, input driver, configuration and the existing
Reversebolt binary hashes before testing. The product is unchanged from the
automatic-checks preview. Run two fresh isolated browser sessions of the same
original Javascript Tetris source used in the prior development evaluation,
with new profiles and external requests blocked. Do not rerun failed cases.

Use the fixed prior key schedule and 16 MiB memory budget. Choose the accessible
renderer with the largest positive three-second CPU delta, PID as tie-break;
this is evaluation setup, not product understanding. Attach with the default
automatic sixteen-capture pass, no local vision model, and no manually chosen
track. The engine chooses and freezes any numeric finding at moment twelve.

After capture twelve, pause the evaluation input driver and wait for its
acknowledgement that no key remains held. Keep it paused through capture fourteen,
then resume the original schedule. Pause and acknowledge again after capture
sixteen. The game itself is never suspended or paused, and gravity may continue.
The driver enforces the owned foreground window and Anode session before inputs.
Retain all missing holds, changed-during-capture moments and game endings.

Once the automatic job completes, retain the current prediction check. Case one
selects candidate index zero; case two selects the final candidate index. These
rules are fixed before either run and never use game oracle values or addresses.
Prepare the latest observed value plus three through ordinary preparation to
record its result, then through explicit probe preparation for that fixed
candidate. If the candidate is contradicted, unavailable, overlapping-ambiguous
or otherwise refused, retain the abstention and do not try another candidate.

For an available plan only, verify that its process identity equals the selected
renderer and that its patch is the reviewed 1–8-byte proposal, then apply it once.
Record the automatic observation, wait 750 ms, record a further observation,
and attempt the existing guarded restoration once. After successful restoration,
wait 750 ms and observe again. No force restoration or repeated native write is
allowed. If an exception interrupts a confirmed written trial before restoration
was attempted, inspect journal status and attempt one guarded cleanup restoration.
Uncertain outcomes never authorize a retry. Close the owned game at the end.

The evaluator's independent oracle reads the original game's actual score,
display score, painted DOM score, board/current piece and playing state. It
records timing around each operation. No oracle, layout, source-derived address
or label is supplied to the product. Report whether the visible number and the
game's own score variable responded, including no response, ordinary game changes,
restoration refusals and hidden-effects limits. A source-variable response is
scoped evidence of influence in this run, not complete game-state recovery or a
general semantic control. The oracle itself can allocate additional copies.

Reuse the unchanged OCR scorer, fixed 200 ms oracle timing limit and geometry
rules from the prior study. Preserve raw evidence, input acknowledgements,
delivered-key order, hash checks, all failures and the unrevised selection.
These exposed development-game tests are not withheld generalization acceptance.
No manual screenshot review or manual gameplay is needed.
