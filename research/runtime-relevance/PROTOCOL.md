# Raw-label relevance review

The prior five-case naming replay completes, but the menu still proposes device
preferences despite instructions to exclude them. Lexical grounding proves that
the names came from observed text; it does not prove gameplay relevance.

Test a separate, blinded review of each accepted primary candidate. Supply only
its complete type/field labels and exact same-object text, with a local index.
Do not supply the generator's proposed name, question, explanation, numeric
value, path identifier, activity interpretation or game title. Names in observed
metadata remain available as evidence, not permission to use remembered code.
Classify every candidate as gameplay, application configuration, implementation
detail or unclear. Require exact own-candidate citations for non-unclear results.
Keep a short cautious reason. Unknown is retained, never an automatic rejection.

This is a fallible second interpretation by the same local model, not independent
verification. Keep it behind a research feature. Do not change card publication,
MCP tools, metadata naming or the desktop preview merely because classification
finishes. No current candidate is removed. A future relevance policy needs evidence
about false exclusions, particularly hidden rules, asset configuration, camera
behaviour and world appearance. There are no game/field-specific exclusion lists.

Freeze source, the research-only executable, these scripts, all saved inputs and
model identity before inference. Reuse the five `bounded-type-selection-v1`
receipts and inventories without rerunning naming. Execute once each: all five
original candidate batches; reversed candidate order for `latest` and `menu`;
and an opaque-label version of the Vampire candidates with object text removed.
The empty original opaque batch must trigger no model inference. The transformed
cases are robustness checks on known reports, not fresh game evidence.

Retain failures and every raw model response without prompt tuning or retries.
Compare categories by exact source path across reordered cases. Report category
counts, reasons and citations for all candidates, including any inconsistent or
unexpected classification. In the opaque transformation, an unclear result is
appropriate; a confident gameplay category has no semantic support. The known
device-preference case is a development diagnostic, not a measured false-positive
rate. Small known samples cannot prove semantic accuracy or generalization.

One request per nonempty batch, at most twelve candidates, 12,000 prompt bytes,
16,384 context tokens and a candidate-count-based bounded output. Preserve request
evidence on incomplete responses or model identity errors. Recheck the exact
prompt/schema/options, response, citations, source scope and evaluated input-token
headroom during offline audit. No game, screenshot, input or process memory
access is required. Default desktop/MCP builds must not enable this research code.
